## 用户需求

在 KathyEngine 中引入四项高密度谱面性能优化机制，并与既有「低延迟模式」联动，目标是降低 SPAM 等超密集谱面下的卡顿与帧率波动，同时不改变正常游玩的判定逻辑与视觉观感：

## 核心功能

- **每帧生成预算（#2，自有改进）**：不做「会丢音符的硬上限」，而是限制单帧 `while` 生成循环内新建音符精灵的数量上限 `maxNotesPerFrame`。卡顿后积压的过期音符不会在同一帧被一次性创建成几百个精灵（避免死亡螺旋），而是分摊到后续帧，配合「过期即时结算」真正越界的音符直接结算、不入组。默认 0 = 关闭（无限，保持原行为）。
- **动态生成距离（#3）**：开启 `dynamicNoteSpawn` 后，音符前瞻生成时间随 `songSpeed` 缩短（`spawnTime` 折算），高速谱面音符更靠近判定线才出现，同屏数量自然下降。
- **过期音符即时结算（#4）**：生成循环内，若某音符 `strumTime` 已远超 `noteKillOffset` 且非 sustain，直接用一次性 `Note` 走 `noteMiss` 结算（对手方音符直接跳过），不加入任何渲染组、不参与逐帧绘制与物理。复用既有 `noteKillOffset` 阈值，确保语义与现有「滚出后强制 miss」完全一致、零判定偏差；sustain 项因 parent/tail 引用链不跳过，仍走原路径。
- **关闭逐音符 Lua 回调（#5）**：开启 `disableNoteLua` 后，跳过 `onSpawnNote` / `goodNoteHit` / `goodNoteHitPre` / `noteMiss` / `opponentNoteHit` / `opponentNoteHitPre` 的 `callOnLuas`/`callOnHScript`。关闭时按「不拦截」处理，保留原有 `Function_Stop` 短路语义（等价于原 result 为 Continue）。
- **低延迟联动**：开启既有 `lowLatency` 时强制 `instantResolveExpired = true` 且 `disableNoteLua = true`，形成一套完整低延迟/低负担组合，与已落地的 `autoResync`/`hideMissedNotes` 协同。

## 技术栈

- 语言/引擎：Haxe + HaxeFlixel（沿用现有项目，无新增依赖）
- 配置存储：`ClientPrefs`（SaveVariables 结构体 + `@:structInit` 默认值）
- 配置 UI：`ExtraGameplaySettingSubState`（`addOption(new Option(...))` 模式）
- 生成路径：既有的「优化加载（`useOptimizedLoading`）」与「传统加载」两条 spawn 循环均需适配

## 实现方案

### 总体策略

在既有音符生成循环、判定回调、以及 `lowLatency` 联动三处插入受设置控制的行为分支，新增四个 `ClientPrefs` 字段并在设置界面暴露。不改动判定窗口计算、命中判定与回放记录逻辑，仅影响「每帧生成多少」「何时生成」「是否渲染过期音符」「是否触发逐音符脚本」。

### 关键决策与权衡

1. **每帧生成预算（低风险，自有改进）**

- 现状：生成循环 `while(...)` 在单帧内可能一次性 spawn 大量音符（尤其卡顿恢复后 `unspawnNotes` 积压）。
- 方案：引入 `maxNotesPerFrame`（默认 0=关闭）。在两条生成循环内用计数器限制本帧新建精灵数量；达到上限即 `break`，剩余音符留到下一帧。这与「会丢音符的硬上限」不同——音符只是延后一帧生成，永不丢失。
- 与 #4 配合：真正越界的过期音符走即时结算（不入组），预算只约束「仍需正常显示的音符」，二者互补。

2. **动态生成距离（低风险）**

- 现状：`spawnTime` 固定（约 2000ms 前瞻），高速谱面同屏音符仍偏多。
- 方案：`dynamicNoteSpawn` 为真时，将前瞻从固定 `spawnTime` 折算为 `spawnTime / max(songSpeed, 1)`（优化路径第 3313 行 `time` 计算处、传统路径第 3414 行处）。songSpeed 越高前瞻越短，同屏实体越少。
